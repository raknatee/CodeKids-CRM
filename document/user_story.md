# User Stories & BDD Scenarios: Customer Relationship Management (CRM) System

## Epic 1: การจัดการข้อมูลลูกค้าและประวัติการติดต่อ (สำหรับ Data Entry Admin)
**เป้าหมาย:** ลดความซ้ำซ้อนของการบันทึกข้อมูลข้ามปี ลดเวลาจัดการ Ads_ID และเก็บประวัติเป็นแบบ Ticket Log

### User Story 1.1: การจัดการข้อมูลข้ามปีโดยไม่ต้องคัดลอก (Cross-year Data Update)
* **As a** Data Entry Admin
* **I want to** ค้นหาและแก้ไขข้อมูลลูกค้าเก่าที่มีในระบบได้ทันที
* **So that** ฉันไม่ต้องเสียเวลา Copy ข้อมูลจากไฟล์ของปีเก่ามาสร้างบรรทัดใหม่ในปีปัจจุบัน
* **BDD Scenario:**
  * **Given:** ลูกค้าชื่อ "คุณส้ม" มีข้อมูลอยู่ในระบบตั้งแต่ปี 2025
  * **When:** แอดมินค้นหาชื่อบัญชีหรือ uuid(Line) ของคุณส้มในปี 2026 และทำการกด "แก้ไขข้อมูล"
  * **Then:** ระบบจะแสดงโปรไฟล์เดิมของคุณส้ม และอนุญาตให้เพิ่ม Ticket การติดต่อของปี 2026 ได้โดยที่ข้อมูลยังรวมอยู่ที่ Customer ID เดิม

### User Story 1.2: การสแกนรูปภาพเพื่อดึง Ads_ID อัตโนมัติ (OCR for Ads_ID)
* **As a** Data Entry Admin
* **I want to** อัปโหลดภาพหน้าจอ (Screenshot) ที่มีรหัส Ads_ID เพื่อให้ระบบดึงตัวเลขให้อัตโนมัติ
* **So that** ฉันไม่ต้องเสียเวลาพิมพ์รหัสยาวๆ ป้องกันการพิมพ์ผิด และไม่ต้องคอยเช็กว่ารหัสนี้ซ้ำกับที่เคยวางไปแล้วหรือไม่
* **BDD Scenario:**
  * **Given:** แอดมินได้รับภาพแคปหน้าจอ Ads_ID จากลูกค้าที่ทักเข้ามาบน Facebook
  * **When:** แอดมินอัปโหลดรูปภาพลงในช่อง "เพิ่ม Ads_ID"
  * **Then:** ระบบจะทำ OCR อ่านตัวเลข Ads_ID ออกมา, ตรวจสอบว่ามี Ads_ID นี้ในประวัติของลูกค้ารายนี้หรือยัง, หากยังไม่มีระบบจะบันทึกให้อัตโนมัติ หากมีแล้วระบบจะแจ้งเตือนว่า "บันทึก Ads_ID นี้แล้ว"

### User Story 1.3: การเก็บบันทึกความสนใจแบบ Ticket Log (Customer Journey Log)
* **As a** Data Entry Admin
* **I want to** บันทึกความสนใจหรือสิ่งที่ลูกค้าทักมาถามเป็น "Ticket" รายครั้ง (แยกตามวันที่ติดต่อ)
* **So that** ฉันไม่ต้องลบหรือเขียนทับข้อมูลความสนใจเดิม และสามารถดูประวัติ Customer Journey ได้
* **BDD Scenario:**
  * **Given:** ลูกค้าเคยมี Ticket สนใจ "คลาส Coding" เมื่อเดือนมกราคม
  * **When:** ลูกค้าทักมาใหม่ในเดือนมีนาคมเพื่อถามเรื่อง "Techzania Camp" และแอดมินสร้าง Ticket ใหม่
  * **Then:** ระบบจะแสดงประวัติว่า ลูกค้ารายนี้มี 2 Tickets ทำให้เห็น Journey ว่าความสนใจเปลี่ยนไปหรือเพิ่มเติมจากอดีตอย่างไร

## Epic 2: การขายและการวิเคราะห์ความสัมพันธ์ครอบครัว (สำหรับ Sale Admin)
**เป้าหมาย:** รวมศูนย์ข้อมูลการติดต่อของครอบครัว และบันทึกข้อมูลเชิงลึกของนักเรียน

### User Story 2.1: การแสดงผลความสัมพันธ์ของครอบครัว (Family Mapping)
* **As a** Sale Admin
* **I want to** เห็นแผนผังความสัมพันธ์ว่าใครคือพ่อ/แม่ ใครคือลูก และพ่อแม่ติดต่อมาจากช่องทางไหนบ้าง
* **So that** ฉันสามารถให้บริการได้ถูกคน ไม่ต้องถามคำถามซ้ำซ้อนแม้ว่าพ่อกับแม่จะสลับกันทักมาจากคนละแพลตฟอร์ม
* **BDD Scenario:**
  * **Given:** มีการผูกข้อมูลว่า คุณพ่อ (ติดต่อผ่าน Line) และ คุณแม่ (ติดต่อผ่าน FB) เป็นผู้ปกครองของ "น้องเอ"
  * **When:** คุณแม่ทัก Facebook มาถามข้อมูลของน้องเอ
  * **Then:** ระบบแชต/หน้าจอของ Sale จะแสดงโปรไฟล์ครอบครัว ให้เห็นว่าคุณพ่อเคยทัก Line มาถามเรื่องนี้แล้วเมื่อวาน ทำให้ Sale สามารถตอบต่อยอดจากข้อมูลเดิมได้ทันที

### User Story 2.2: การบันทึกข้อมูลเชิงลึกเฉพาะบุคคล (Student Insights)
* **As a** Sale Admin
* **I want to** บันทึกข้อมูลภูมิหลัง, ประสบการณ์, และความต้องการพิเศษของเด็กแต่ละคน
* **So that** ทีมงานทุกคนมีข้อมูลบริบทที่ตรงกันเพื่อใช้ในการแนะนำหลักสูตรที่เหมาะสมที่สุด
* **BDD Scenario:**
  * **Given:** Sale Admin กำลังพูดคุยและทราบว่าเด็กมีภาวะสมาธิสั้น (ADHD)
  * **When:** Sale Admin พิมพ์บันทึกในช่อง "Student Insight" ของโปรไฟล์เด็ก
  * **Then:** ข้อมูลนี้จะถูกติดป้ายกำกับ (Tag) เป็นข้อมูลสำคัญ ซึ่งจะแสดงผลให้ผู้บริหารหรือคุณครูเห็นเมื่อเปิดโปรไฟล์ของเด็กคนนี้

## Epic 3: การให้คำปรึกษาและภาพรวมข้อมูล (สำหรับ Executive / ผู้บริหาร)
**เป้าหมาย:** รวมข้อมูลการเรียน ข้อมูลการขาย และข้อเสนอแนะไว้ใน Timeline เดียว

### User Story 3.1: ไทม์ไลน์ประวัติการเรียนรู้ (Study Journey Timeline)
* **As an** Executive
* **I want to** ดูประวัติแบบ Timeline ที่รวมทั้งประวัติการเรียน, บันทึกจาก Sale, และคอมเมนต์จากคุณครูไว้ในหน้าเดียว
* **So that** ฉันสามารถอ่านข้อมูลย้อนหลังทั้งหมดได้อย่างรวดเร็วเพื่อใช้ประกอบการให้คำปรึกษาผู้ปกครอง
* **BDD Scenario:**
  * **Given:** ผู้บริหารเปิดโปรไฟล์ของ "น้องบี"
  * **When:** ผู้บริหารคลิกที่แท็บ "Study Journey Timeline"
  * **Then:** ระบบจะแสดงเส้นเวลาเรียงลำดับจากอดีตถึงปัจจุบัน ประกอบด้วย: วันที่ทักครั้งแรก (Sale) -> คลาสที่ลงเรียน (System) -> คอมเมนต์หลังเรียนจบ (Teacher)

### User Story 3.2: การบันทึกคำปรึกษาจากผู้บริหาร (Executive Consulting Feedback)
* **As an** Executive
* **I want to** บันทึกข้อเสนอแนะและผลการให้คำปรึกษา (Consultation Insight) ลงใน Timeline ของเด็กโดยตรง
* **So that** ข้อมูลทั้งหมดถูกรวมไว้ที่ศูนย์กลาง และทีม Sale หรือครูสามารถนำคำแนะนำของฉันไปปฏิบัติตามได้
* **BDD Scenario:**
  * **Given:** ผู้บริหารให้คำปรึกษาผู้ปกครองเสร็จสิ้น
  * **When:** ผู้บริหารพิมพ์สรุปคำปรึกษาและกด "Add Executive Insight" ในหน้า Study Journey ของเด็ก
  * **Then:** ระบบจะบันทึกข้อความนั้นลงใน Timeline นั้น พร้อมทำไฮไลต์ให้ทีมงานทราบว่าเป็นคำแนะนำพิเศษจากผู้บริหาร

## Epic 4: การทำงานทั่วไปและระบบพื้นฐาน (General Operations & Core System)
**เป้าหมาย:** เพื่อให้ผู้ใช้งานเข้าถึงระบบได้อย่างปลอดภัย ค้นหาข้อมูลได้รวดเร็ว และป้องกันความผิดพลาด

### User Story 4.1: ระบบค้นหาครอบจักรวาล (Global Search)
* **As a** System User (Admin, Sale, Executive)
* **I want to** ค้นหาข้อมูลลูกค้าจากช่องค้นหาเดียว (Global Search) โดยใช้คีย์เวิร์ดอะไรก็ได้ เช่น ชื่อพ่อ, ชื่อลูก, เบอร์โทร, หรือ Line Display Name
* **So that** ฉันสามารถเข้าถึงโปรไฟล์ของครอบครัวนั้นได้อย่างรวดเร็วโดยไม่ต้องเสียเวลานึกว่าต้องไปค้นหาที่เมนูไหน
* **BDD Scenario:**
  * **Given:** ผู้ใช้งานอยู่ในหน้าใดๆ ของระบบและมีช่องค้นหาอยู่ด้านบน
  * **When:** ผู้ใช้งานพิมพ์ตัวเลข "S2400" (รหัสนักเรียน) หรือคำว่า "น้องเอ" (ชื่อเด็ก) หรือ "คุณสมชาย" (ชื่อผู้ปกครอง) ลงในช่องค้นหา
  * **Then:** ระบบจะแสดง Dropdown แนะนำผลลัพธ์ที่ตรงกันทันที โดยแบ่งหมวดหมู่ให้เห็นชัดเจนว่าผลลัพธ์นี้คือ ชื่อผู้ปกครอง หรือ ชื่อนักเรียน เมื่อคลิกจะพาไปสู่หน้าโปรไฟล์นั้นๆ ทันที

### User Story 4.2: การป้องกันการสร้างข้อมูลซ้ำซ้อน (Data Deduplication & Validation)
* **As a** System
* **I want to** ตรวจสอบเบอร์โทรศัพท์และรหัส Platform (เช่น FB Username, Line UUID) ทุกครั้งที่มีการสร้างโปรไฟล์ใหม่
* **So that** ป้องกันไม่ให้พนักงานเผลอสร้างโปรไฟล์ผู้ปกครองคนเดียวกันซ้ำเป็น 2 บัญชี
* **BDD Scenario:**
  * **Given:** ในฐานข้อมูลมีคุณแม่ชื่อ "คุณสมหญิง" ใช้เบอร์โทร "081-111-2222" อยู่แล้ว
  * **When:** แอดมินคนใหม่พยายามจะกด "สร้างผู้ปกครองใหม่" และกรอกเบอร์ "081-111-2222"
  * **Then:** ระบบจะล็อกปุ่มบันทึก และแจ้งเตือนสีแดงว่า "เบอร์โทรศัพท์นี้มีอยู่ในระบบแล้ว" พร้อมแสดงปุ่ม "ไปยังโปรไฟล์ของคุณสมหญิง" เพื่อให้อัปเดตข้อมูลแทน

### User Story 4.3: ระบบการแจ้งเตือนและการติดตามผล (Task & Follow-up Notifications)
* **As a** Sale Admin / Data Entry Admin
* **I want to** ตั้งค่าวันที่ต้องติดตามผล (Follow-up Date) ในแต่ละ Ticket การติดต่อ
* **So that** ระบบจะแจ้งเตือนฉันเมื่อถึงเวลาที่ต้องทักไปหาลูกค้า เพื่อไม่ให้หลุดจังหวะการขาย
* **BDD Scenario:**
  * **Given:** แอดมินสร้าง Ticket ว่าลูกค้าสนใจคลาสเรียน และตั้งค่า "Follow-up" ไว้ในอีก 3 วันข้างหน้า
  * **When:** ถึงวันที่กำหนด (หรือเมื่อแอดมินล็อกอินเข้าระบบในวันนั้น)
  * **Then:** ระบบจะแสดง Notification แจ้งเตือนว่า "ถึงเวลาติดตามผล: คุณสมชาย เรื่องคลาส Coding"

### User Story 4.4: การจัดการสิทธิ์การเข้าถึงข้อมูล (Role-Based Access Control - RBAC)
* **As a** System Administrator
* **I want to** กำหนดสิทธิ์และบทบาท (Role) ของผู้ใช้งานแต่ละคน เช่น Admin กรอกข้อมูล, Sale, Manager, Executive
* **So that** ผู้ใช้งานจะเห็นและแก้ไขได้เฉพาะข้อมูลที่ตรงกับหน้าที่ของตนเอง ป้องกันการแก้ไขข้อมูลโดยไม่ได้ตั้งใจ
* **BDD Scenario:**
  * **Given:** มีการตั้งค่าสิทธิ์ให้ "Data Entry Admin" ไม่สามารถดูข้อมูล "ยอดขายรวม (Revenue)" ได้
  * **When:** ผู้ใช้งานที่ล็อกอินด้วยสิทธิ์ Data Entry Admin เข้าสู่ระบบ
  * **Then:** ระบบจะซ่อนเมนู "Dashboard สรุปยอดขาย" และ "Executive Insight" ออกจากหน้าจอ และไม่สามารถเข้าถึง URL ของหน้านั้นได้

## Epic 5: การจัดการคุณภาพข้อมูลและการวัดผล (Data Quality & Performance Analytics)
**เป้าหมาย:** เปลี่ยนข้อมูลดิบให้เป็นระบบอัตโนมัติ ลดข้อผิดพลาดจากคน และเพิ่มความสามารถในการวิเคราะห์ประสิทธิภาพ

### User Story 5.1: ระบบคำนวณและติดตามความเร็วในการตอบกลับ (SLA Tracking)
* **As an** Executive / Manager
* **I want to** ดูรายงานค่าเฉลี่ยความเร็วในการตอบแชต (Response Time) ของแอดมิน
* **So that** ฉันสามารถประเมินประสิทธิภาพการทำงานของทีม และมั่นใจได้ว่าลูกค้าจะไม่รอนานจนหลุดความสนใจ
* **BDD Scenario:**
  * **Given:** ระบบมีการประทับเวลา (Timestamp) อัตโนมัติเมื่อสร้าง Ticket ใหม่ และเมื่อแอดมินพิมพ์ตอบกลับครั้งแรก
  * **When:** ผู้บริหารเปิดหน้า "Dashboard ประสิทธิภาพทีม"
  * **Then:** ระบบจะคำนวณส่วนต่างของเวลา และแสดงกราฟแท่งเปรียบเทียบ "เวลาตอบกลับเฉลี่ย" ของแอดมินแต่ละคน พร้อมไฮไลต์สีแดงหากแอดมินคนใดใช้เวลาตอบเกินเกณฑ์ที่กำหนด

### User Story 5.2: การติดตามลูกค้าที่กลับมาติดต่อซ้ำอัตโนมัติ (Automated Retention & Cohort Tracking)
* **As a** Marketing Staff
* **I want to** ดูรายงานว่าลูกค้าที่เคยติดต่อในเดือน/ปีที่แล้ว มีการกลับมาเปิด Ticket ใหม่ (ทักซ้ำ) ในเดือนปัจจุบันกี่เปอร์เซ็นต์
* **So that** ฉันไม่ต้องมานั่งเช็กกล่องข้อมูลทีละเดือนด้วยตัวเอง และสามารถวิเคราะห์อัตราการกลับมาของลูกค้าได้
* **BDD Scenario:**
  * **Given:** ระบบบันทึก Ticket Log การติดต่อทุกครั้งของลูกค้าไว้ในฐานข้อมูลอยู่แล้ว
  * **When:** ฝ่ายการตลาดเลือกเมนู "Retention Report" และเลือกกลุ่มลูกค้าปี 2025
  * **Then:** ระบบจะดึงประวัติ Ticket มาคำนวณอัตโนมัติ และแสดงผลเป็นตารางหรือกราฟว่า "ลูกค้ากลุ่มปี 2025 กลับมาติดต่อใหม่ในปี 2026 จำนวนกี่คน" โดยไม่ต้องมีการเพิ่มคอลัมน์ใดๆ

### User Story 5.3: ระบบจัดมาตรฐานข้อมูลพื้นที่และภูมิศาสตร์ (Standardized Location Input)
* **As a** Data Entry Admin
* **I want to** เลือกจังหวัด อำเภอ และตำบล จาก Dropdown List หรือระบบ Auto-complete แทนการพิมพ์เอง
* **So that** ข้อมูลภูมิศาสตร์ของลูกค้าจะเป็นมาตรฐานเดียวกันทั้งหมด ง่ายต่อการดึงข้อมูลไปทำโฆษณาเจาะจงพื้นที่
* **BDD Scenario:**
  * **Given:** แอดมินกำลังสร้างหรืออัปเดตโปรไฟล์ผู้ปกครอง
  * **When:** แอดมินพิมพ์คำว่า "ขอน" ลงในช่องที่อยู่
  * **Then:** ระบบจะแสดงตัวเลือก "ขอนแก่น" ขึ้นมาให้เลือกคลิกทันที ป้องกันการพิมพ์ชื่อจังหวัดผิดพลาด

### User Story 5.4: กระดานภาพรวมสถานะการขาย (Sales Pipeline / Kanban Board)
* **As a** Sale Admin
* **I want to** เห็น Ticket การติดต่อของลูกค้าทุกคนในรูปแบบกระดาน (Kanban Board)
* **So that** ฉันสามารถลาก (Drag & Drop) รายชื่อลูกค้าเปลี่ยนสถานะได้ง่ายๆ และรู้ว่าวันนี้ต้องเร่งปิดการขายกับใคร
* **BDD Scenario:**
  * **Given:** ลูกค้าอยู่ในสถานะ "รอชำระเงิน"
  * **When:** ลูกค้าส่งสลิปโอนเงินมา และ Sale Admin ลากการ์ดของลูกค้ารายนี้ไปที่ช่อง "สมัครแล้ว (Paid)"
  * **Then:** ระบบจะอัปเดตสถานะในฐานข้อมูลเป็น Paid ทันที และอัปเดตข้อมูลบนระบบ
